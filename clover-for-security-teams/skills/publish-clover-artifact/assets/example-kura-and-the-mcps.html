For TAMs and SEs

One feature, plan to report

Clover keeps one security context per application: what it does, how it is built, what was reviewed, decided and fixed. Three integrations carry that context into the coding agents a customer already runs. Kura pushes it into every coding session by itself. The two MCPs let a person pull from it when they ask.

Here is where each one comes in on a single feature.

  1. 1
    KuraSecurity team, once

    Kura goes out to every developer

    An admin rolls Kura out through Claude managed settings, a Cursor team marketplace or MDM. It starts in Visibility mode: developers notice nothing, and every coding session shows up in Clover under Agentic Development, Visibility and Coverage. When the team is ready, the admin moves it to Advisory or Enforcement.

    Doc: Connecting Kura to coding agents
  2. 2
    KuraDeveloper, in the coding agent

    The plan arrives with its security requirements

    A developer plans a feature in Claude Code. When they exit plan mode, in Advisory or Enforcement, Kura adds the requirements for this task, each tied to a named threat in the application's threat model, and attaches the plan to the relevant security review. The developer asked for nothing. The hooks ran as part of the session.

    Doc: About Kura
  3. 3
    Developers MCPDeveloper, in the editor

    The developer answers the review from Cursor

    The feature's design doc has a security review. From Cursor, the developer opens it, reads its threats and requirements, and marks a threat covered by design with a written reason. Clover checks the reason against that threat's attack mechanism before it records anything. A response of irrelevant or risk accepted goes to the security team's queue.

    Doc: Clover for Developers
  4. 4
    Security Teams MCPSecurity lead, in their own agent

    The security lead asks about the whole program

    From Claude, the security lead runs /rank-top-threats across the organization, then /plan-remediation on what comes back. With an API token, the same connection can run a scheduled job that sends the CISO the three reviews that matter most every morning.

    Doc: Clover for Security Teams

Each step works without the others. A customer can start at any one of them and add the rest later.

Kura's three enforcement levels

Visibility

Kura observes and reports. Nothing appears in the developer's session.

Advisory

Requirements appear through the coding agent as optional context. Nothing is blocked.

Enforcement

Non-compliant work does not proceed until the requirements are met.

Field answers

When the customer says

Six things customers have said on calls, what to answer, and which doc section to send.

We'll route Kura through our MCP gateway.

Kura is a plugin that adds hooks to the agent, so it never passes through an MCP gateway. What it needs is network access to api.cloversec.io and auth.cloversec.io. If those are blocked, Kura lets the session continue and does nothing visible.

Send: Connecting Kura, Air-gapped install
Every new MCP has to go through my team's approval.

Kura is not an MCP. Its token carries one scope, Clover Coding Plugin, and reaches the hook endpoints only. In Cursor, the Kura setup also adds a Clover MCP server. Say so up front: it is an empty server with no tools, and its only job is to pass Kura its credentials in an organization-wide install.

Send: Connecting Kura, Before you start
So every developer has to install the hooks plugin?

No. An admin rolls it out once through Claude managed settings, a Cursor team marketplace or MDM, and developers get it on their next session. Per-developer install is for testing or unmanaged machines.

Send: Connecting Kura, Organization rollout
We connect MCPs with user credentials, never shared ones.

That rule fits both MCPs, which sign in as a person. Kura uses one client credential for the hook endpoints. In Claude Code, the dashboard attributes each session to a developer through that developer's own Claude sign-in.

Send: Connecting Kura, Troubleshooting
I think I have both MCPs going.

Ask what they can see. Reviews, applications and reporting across the program means Security Teams. Only reviews of their own changes means Developers.
